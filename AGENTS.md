## Start here

Read this file first, then **`types/database.ts`** — it holds every row type and
domain enum and is the closest thing to a schema file. There is **no ORM and no
`prisma/schema.prisma`**: the schema lives in numbered SQL under
`supabase/migrations/`, and `types/database.ts` is the hand-maintained TS mirror
of it.

Then open only what the task needs, using [Layout](#layout) as the map. The
`components/schools/` tree holds most of the business logic and most of the
subtle bugs.

Before changing anything, read
[What is real, and what only LOOKS real](#what-is-real-and-what-only-looks-real).

## What this is

**Teach AI for India** — the operations platform for a student-led AI-literacy
movement. University campus teams run outreach to schools, deliver a bounded
4-session program, and claim reimbursements. The app is the system of record for
that whole pipeline, plus a public marketing site.

Production: deployed on Vercel. Database: hosted Supabase (`main` branch is
production).

## Stack

Next.js 16 (App Router) · React 19 · TypeScript 5.7 · Tailwind v4 · shadcn/ui
(Radix) · Supabase (Auth/Postgres/Storage/RLS) · zod · Resend · sonner ·
lucide-react · Framer Motion.

No test framework is configured. **Verification means:**

```bash
npx tsc --noEmit    # must be clean
npx next build      # must exit 0
```

Run both before claiming work is done. `next build` rewrites `next-env.d.ts` and
`tsconfig.tsbuildinfo` — both are tracked, so `git checkout --` them before
committing rather than committing build noise.

### Operational phases

Once a school is `sessions_active`, `operational_phase` tracks a 7-step
sub-workflow (`lib/constants/operational-phases.ts`):

```
team_preparation → team_ready → execution_planning → execution_ready
                 → session_1 … session_4
```

### The approval chain (most bug-prone area)

**Execution plan:** Exec Lead submits → Campus Lead reviews → Finance Lead
reviews budget → `approved` → school becomes `execution_ready`.

Statuses (`execution_plan_status`): `draft`, `submitted`,
`campus_changes_requested`, `campus_approved`, `finance_changes_requested`,
`approved`. **There is no `rejected` member** — `approved` is the only terminal
state, and "open" means `status <> 'approved'`.

Invariant since `0069`: **one open execution plan per school**, enforced by a
partial unique index. `submit_school_execution_plan()` reuses the open plan
rather than inserting a rival row.

Budget is allocated across four lines (transport, materials, equipment, other);
`total_budget` is a generated column summing them. Every approval request —
notification body *and* audit detail — carries the total **and** all four
categories, via `execution_plan_budget_summary()`.

**Session delivery:** Exec Lead reports (with mandatory Drive photo link +
Docs attendance link, stored in `media_assets`) → Campus Lead verifies. When all
4 sessions are `verified` the school auto-completes.

## What is real, and what only LOOKS real

Some of what renders is not backed by live data. Know which is which before you
"fix" a number or trust a screen.

**The database is production.** `main` deploys to Vercel against the hosted
Supabase project, and migrations are applied by pasting into the Supabase SQL
editor or running `supabase db push` — both hit production directly. There is no
staging project. Anything destructive (`delete`, `drop`, `update` without a
tight `where`) is operating on real campus data. Migration `0069` deletes rows;
that was deliberate and reviewed. Treat every migration as a production change.

**Synthetic data that renders as if real:**

| Where | What |
|---|---|
| `components/schools/planning-panel.tsx` | When `schoolDetail` is absent it substitutes a `mockSchool` with `dise_code: 'EXAMP123'`, `campus_id: 'campus-1'` — and that object feeds the onboarding readiness gate, so the gate can pass on fabricated values. |
| `lib/data/public.ts` | `FALLBACK_IMPACT` — the public site's impact figures (schools reached, students impacted, …) fall back to hardcoded last-known-good constants whenever Supabase is unreachable or unconfigured. The marketing site therefore always shows numbers, real or not. |
| `actions/auth.ts` | With Supabase unconfigured, password reset accepts a hardcoded `mockUsers` list so the flow can be demoed offline. |
| `placeholder_search_results.json` (repo root) | A stray developer scratch file of grep output with absolute `C:\Projects\…` paths. Not application data, not read by anything. |

**Graceful degradation is by design:** with no Supabase env the public site
renders on fallbacks and auth/middleware no-op. Dashboards need a real project.
So "it renders" is not evidence that a query works.

## Conventions

### Server actions

Every action returns a state object, consumed via `useActionState`:

```ts
type ActionState = { ok?: boolean; error?: string; message?: string; values?: Record<string,string> }
```

Pattern: `requireUser()` → check capability via `lib/auth/rbac` → parse with the
domain zod schema → call a Supabase RPC → `revalidatePath()` → return state.
Echo submitted `values` back on error so the form can repopulate — **never**
include passwords.

Validate inputs *before* hitting an RPC. A raw Postgres error reaching the UI
(`invalid input syntax for type uuid: ""`) means a guard is missing.

### Forms

Client components using `useActionState`. On success call `useFormSuccess()`
(`hooks/use-form-success.ts`) — it fires a sonner toast and `form.reset()` once
per success, tracked by state identity so re-renders can't duplicate it.

Two things to remember:
- `form.reset()` only clears **native inputs**. React-controlled state (chips,
  synced numeric fields) must be reset explicitly via `onSuccess`.
- **Edit forms should toast without clearing** — wiping a record the user just
  saved destroys the view.

### Numerics from Supabase

PostgREST can return `numeric` columns as **strings**, where `a + b`
concatenates instead of adding. Always `Number()` before arithmetic. Prefer
recomputing a total from its parts over trusting a stored/generated total, so
the total always matches the breakdown displayed beside it.

### Migrations

`supabase/migrations/NNNN_description.sql`, applied in order, **append-only** —
never edit one that may have been applied. Two migrations share `0061` and
`0066`; that's existing drift, don't replicate it.

House rules learned the hard way:
- Check the enum before using a value. `ALTER TYPE ... ADD VALUE` can't be used
  in the same transaction that added it (`55P04`) — split across migrations.
- `CREATE OR REPLACE FUNCTION` **cannot change a signature**. A different
  parameter list creates an *overload*, and PostgREST then can't resolve the
  call. `DROP FUNCTION` the old signature explicitly first.
- Make each statement self-contained. Don't share a temp table across
  statements — `supabase db push` wraps a migration in one transaction, but the
  SQL editor may autocommit per statement.
- Before deleting rows, re-point FKs that are `ON DELETE SET NULL`, or you
  silently orphan the referencing records.

### Applying migrations

Either paste into the Supabase SQL editor (see `supabase/README.md`), or
`supabase db push` — which applies **every** pending migration, not just the new
one. Code depending on a migration must not ship before it is applied.

## Gotchas

- **`README.md` is stale.** Its role list (`mgmt_admin`, `outreach_head`,
  `school_poc`, `viewer`) predates the role realignment in `0025`, and its
  "no public self-registration" claim is wrong — `/signup` exists and is
  admin-approval gated. Trust `types/database.ts` and this file instead.
- The app degrades gracefully without Supabase configured: the public site
  renders with fallback numbers, auth/middleware no-op. Dashboards need a real
  project.
- `SUPABASE_SERVICE_ROLE_KEY` is server-only. Never prefix it `NEXT_PUBLIC_`.
- `components/schools/` holds the most business logic and the most subtle bugs.
  Read the surrounding code before editing.

## Maintaining this file

Part of this file maintains itself; part of it cannot.

**Auto-derived** — everything between `<!-- AUTO:x -->` markers (roles, status
enums, school lifecycle, repo counts) is regenerated from source by
`scripts/sync-agents-md.mjs`. Never hand-edit inside those markers; your edit
will be overwritten. A `.githooks/pre-commit` hook runs the script and stages the
result on every commit, so these blocks cannot go stale.

This is a **git** hook, not an editor hook — it works with any editor, AI tool,
or model. It is not automatic on a fresh clone; each clone must run once:

```bash
git config core.hooksPath .githooks
node scripts/sync-agents-md.mjs --check   # CI-friendly: exits 1 if stale
```

**Hand-written** — everything else. Conventions, gotchas, the approval-chain
narrative, and the warnings about what bit us before cannot be inferred from
source. The pre-commit hook *warns* when structural files change without any
prose update, but it does not block and it cannot write the prose for you.

Update the hand-written sections **in the same commit** as the change, whenever you:

- add/remove/rename a **role**, or change what a role may do
- change the **school lifecycle**, operational phases, or any status enum
- change the **approval chain** or its invariants
- add or change a **convention** other code should follow
- add a top-level **directory**, or move a domain between them
- learn a **gotcha** worth warning the next agent about

Routine bug fixes and UI tweaks don't need an entry. The test is: *would an agent
starting cold be misled by what this file currently says?* If yes, fix it.

The prose counts in [Layout](#layout) are illustrative; the authoritative,
always-current numbers are in the auto-derived block directly beneath it.
